# 轻量需求文档工作流

## 核心目标

按以下优先级工作：

1. 尽快生成一份真实可读、可以继续修改的需求文档。
2. 把会改变产品行为的问题尽量一次性列全，让用户批量确认。
3. 每轮明确告诉用户现在要做什么，以及回复后会发生什么。
4. 用简单的 Markdown 文件管理工作稿、决定和评审结果。

不要让流程记录、编号或校验工作压过需求文档本身。

## 基本原则

- 先从用户原话、附件和已有文档提取需求，再组织成清晰的工作稿。
- 能合理生成工作稿时先生成，不要求用户先回答所有非阻塞问题。
- 只有缺少答案会使需求主体无法成立时，才在生成前暂停。
- 区分用户已确认、AI 建议、待确认和交给 Figma 的表现选择，不把建议写成已确认事实。
- 用户明确修改当前工作稿时，直接更新同一版本；不要因一次意见、一次评审或一次修改升版。
- 文档生命周期只有 `work` 和 `frozen`。沟通、确认、修改和评审期间始终保持 `work`；只有用户明确说“封版”“定稿”或同等指令后才改为 `frozen`。
- 不使用任何哈希、指针、事务、状态一致性或结构校验逻辑，也不运行需求空间校验器。
- 不为了流程完整而创建用户不需要的过程文件。

## Wiki 管理

用户指定的目录就是项目 Wiki 根目录。直接在其中使用：

```text
<wiki-root>/
├── _meta/
│   └── raw/                         # 用户提供的原始材料，可选
└── 需求文档/
    ├── index.md                     # 当前版本、work/frozen、封版时间和下一步
    ├── 需求记录.md                   # 按版本记录决定、开放问题和变更
    ├── 评审记录.md                   # 按版本记录每轮评审
    └── 版本/
        └── <topic-id>_v0.1.md       # 当前工作需求文档
```

不得在用户指定根目录内再创建 `spaces/<project-id>/wiki`、`<project-id>/wiki` 或额外 `wiki/` 包装层。

不要在 `需求文档/` 与上述文件之间增加 `<topic-id>/` 目录。主题通过版本文件名区分，统一由 `需求文档/index.md` 导航。

已有 Wiki 不强制迁移或重建。优先读取 `需求文档/index.md`、当前需求版本、`需求记录.md` 和与本次任务有关的评审记录；旧版遗留的阶段、哈希、OP、COM、账本修订等字段只视为历史信息，不再维护。

需求版本只保留以下生命周期信息；不要增加其他流程状态：

```yaml
document_version: v0.1
lifecycle: work
frozen_at: none
```

封版时改为：

```yaml
lifecycle: frozen
frozen_at: 2026-08-14T15:30:00+08:00
```

`frozen_at` 只在用户明确封版时填写。待确认、待接受、评审中等步骤通过对话和“下一步”说明表达，不保存为生命周期状态。

`需求记录.md` 和 `评审记录.md` 各保留一个文件，文件内容必须按版本划分。所有新增内容只写入当前版本分区，不把不同版本的决定或评审混在一起。

`需求记录.md` 使用：

```markdown
# 需求记录

## v0.1

### 已确认决定

### 开放问题

### 变更记录

## v0.2

### 已确认决定

### 开放问题

### 变更记录
```

`评审记录.md` 使用：

```markdown
# 评审记录

## v0.1

### 2026-08-14 · 第一次评审

### 2026-08-15 · 修改后复审

## v0.2

### 2026-09-01 · 第一次评审
```

同一版本可以有多轮评审，按时间追加在该版本分区下。版本变为 `frozen` 后，其需求记录和评审记录分区也冻结；新需求、新决定和新评审写入下一版本分区。

## 工作步骤

### 1. 建立或恢复主题

- 新主题：确认 Wiki 根目录和主题名称；能从上下文确定时不要重复提问。
- 已有主题：读取 `需求文档/index.md`、当前版本和待确认事项；`work` 时继续修改，`frozen` 时保持不变并为新需求创建下一版本。
- 原始附件可复制到 `_meta/raw/`，但不要改写原始内容。

### 2. 生成需求工作稿

优先写需求正文。根据实际内容组织章节，不套空模板。正文应尽量明确：

- 目标、范围和明确排除项；
- 用户或角色之间确有差异的能力；
- 关键对象及其关系；
- 核心任务、流程和分支；
- 会影响用户操作的状态；
- 权限、失败、撤销、归档等关键结果；
- 交给 Figma 决定的布局、控件和视觉自由。

不在产品需求中展开数据库、API、服务拆分、框架或实现细节，除非它们直接限制用户可见行为。

### 3. 一次性集中确认

在向用户提问前，先完整扫描当前材料和工作稿，把所有会改变范围、角色、流程、状态、权限、反馈或设计结果的问题汇总出来。

默认一次性展示全部重要问题，不限制为 1–3 个，也不要每轮只问一个。问题很多时可以按模块分组，但必须说明是否已经列完；只有内容过多到无法可靠处理时才拆批，并提前列出全部分组。

每个问题包含：

- 为什么需要确认；
- 2–3 个互斥方案；
- 推荐方案和简短理由；
- 会影响文档的哪一部分。

优先提供可批量回复的格式，例如：

```text
采用推荐：Q1-B、Q2-A、Q3-C，更新当前 v0.1。
```

用户批量确认后，一次性更新当前版本和 `需求记录.md` 中对应的版本分区。已经确认的答案不要重复询问。

### 4. 修改当前版本

- 把用户已确认的变化写入同一个 `work` 文件。
- 在 `需求记录.md` 的当前版本分区中简要记录日期、决定和本次变化即可。
- 更新 `需求文档/index.md` 的当前版本、生命周期、开放问题和下一步。
- 不维护历史快照哈希，也不因正文变化创建新版本。

### 5. 可选内容评审

仅在用户要求评审时进行。评审一次性检查：

- 是否忠实覆盖已确认内容；
- 是否存在冲突、歧义或无来源的产品结论；
- 关键角色、流程、状态、权限和失败结果是否闭合；
- 两个合理设计者是否会因规则不清做出业务含义不同的原型；
- 是否混入不必要的技术实现或视觉细节。

一次性列出全部评审项，按 Blocker、Major、Minor、Suggestion 分级。每项给出问题、影响、选项和推荐。评审只追加到 `评审记录.md` 对应的版本分区，未经用户授权不要同时修改需求正文。

### 6. 接受与封版

- 用户接受修改结果后，生命周期仍为 `work`，可以继续补充需求或按用户要求进入评审。
- 用户明确封版当前版本后，把生命周期改为 `frozen`、填写 `frozen_at`，不再修改该文件。
- 封版后的新需求通常创建下一小版本，例如 `v0.1 → v0.2`；版本级别有歧义时一次性询问。

## 每轮输出要求

每次完成生成、修改、提问或评审后，用简洁方式给出：

1. 已完成的结果和可点击文件路径；
2. 当前版本是 `work` 还是 `frozen`，以及流程走到哪一步；
3. 用户现在需要检查或决定的 2–5 个重点；
4. 如果存在产品问题，给出完整问题清单或其文件链接，并明确是否已列完；
5. 1–3 条可直接回复的示例；
6. 回复后会更新什么，以及不会自动发生什么。

用户问“现在该做什么”时，直接给出唯一推荐动作；如有待确认事项，优先让用户一次性批量确认。

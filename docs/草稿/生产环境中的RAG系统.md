## 生产环境面临哪些挑战

生产环境会给检索增强生成（RAG）系统带来全新的运行压力，应对这类挑战所需的技能，和原型搭建阶段截然不同。开启本章节之前，我们先来梳理系统正式面向真实用户使用后，将会迎来哪些全新难题。

上线后遇到的第一类难题，根源在于流量规模扩张。用户数量增多会限制系统吞吐量，既包括系统能够并发处理的请求数量，也涵盖接收请求到返回回答之间的延迟时长。请求量上涨还会带来内存与算力消耗的增加，最终造成成本攀升。在大规模流量下维持系统原生性能，本身就是一大难点。

第二类挑战，来源于用户提问的多样性与不可预测性。即便上线前经过严密测试，也很难预判 RAG 系统将会收到的所有类型提问。即便系统在上线测试阶段表现良好，面对这些从未见过的新问题时，依旧可能出现处理失常的情况。

生产环境中的另一项难题是，现实场景的数据往往杂乱无序。数据碎片化、格式不规范、缺失元数据等问题十分常见。大量数据甚至并非文本格式，而是图片、PDF、幻灯片等形式。如果想要将这些数据纳入知识库，就必须搭建对应的读取解析方案。

安全与隐私问题同样不容忽视。很多 RAG 系统部署的初衷，就是为了对内私有数据、专有资料进行调用。既要保障数据私密性，又要让授权用户在使用 RAG 系统时正常调取数据，这项功能至关重要。

除去以上各类难题，生产环境最严峻的一点在于：一旦出现失误，将会实实在在地对业务造成影响，既可能产生经济损失，也会损害品牌声誉。谷歌刚推出 AI 搜索摘要功能时，系统曾针对某条提问给出建议，告知用户可以吃石头来补充营养。谷歌事后排查问题起因，发现是有用户提问「我应该吃多少块石头？」，这个问题本身无厘头，很难提前预判。系统针对该问题检索资料时，命中了多篇戏谑性质的文章与论坛对话，却没能识别出内容属于玩笑。谷歌后续修复了该问题，还发布博客说明了故障成因。但遭遇过上线事故的大模型产品厂商远不止谷歌一家。多家航空公司的客服机器人曾好心向用户承诺并不存在的优惠折扣。恶意攻击者还会想方设法诱导 RAG 系统，企图免费获取商品、套取内部机密信息。

总而言之，生产环境对于 RAG 系统而言充满考验。因此必须搭建配套体系：在问题爆发前提前预判风险、故障发生后能够定位根源、验证迭代改动确实带来正向优化，这三点至关重要。

我们可以运用多种技术手段来攻克这些生产环境难题。下一课时将介绍第一种解决方案：搭建完备的可观测体系，我们接着学习。

## 实施RAG评估策略

应对生产环境各类挑战，首要的有效举措便是搭建一套完善的可观测系统。
我们先来介绍该系统应当包含的各个组成模块。

可观测平台需要追踪几类不同的数据信息。
第一类是常规软件性能指标，例如延迟、吞吐量、内存占用与算力消耗。
和绝大多数生产级软件系统一样，你需要掌握系统处理的请求总量、单次请求耗时以及资源消耗量。

其次，需要采集各类质量指标。这里所说的质量涵盖方方面面：既包括用户对最终回复的满意度，也包含检索器的召回率。
除了掌握系统的运行速度与运行效率，你还需要确认最终输出结果是否符合预设的质量标准。
信息的采集与上报方式同样十分关键。系统需要持续汇总统计数据，方便你观察性能整体趋势，快速发现性能退化问题。
与此同时，系统还应当留存完整的详细日志。借助日志可以追踪每一条用户提问在 RAG 链路中的完整流转过程，在排查劣质回答的成因时尤为实用。

最后，评估系统最好具备实验能力。当你打算更换大模型、修改系统提示词、调整检索器参数时，既可以在隔离环境中开展定制化实验，也可以在线上生产环境面向真实用户做 A/B 测试。
只要能够监测改动对性能指标与质量指标带来的影响，就能判断是否可以将实验方案正式上线。

了解整体架构后，我们再来聊聊需要重点追踪的具体指标。可以借助「评估范围」与「评估主体类型」两个维度梳理全部指标。

评估范围：本次评估是针对 RAG 系统某个独立组件，还是针对整套系统。
评估主体类型：评估方式分为代码判定、大模型充当裁判、人工反馈三种。
这两个维度可以构成一张网格，各类评估手段都能对应到网格的某个格子之中。
下面逐一讲解两个维度，再说明常见评估方式分别对应网格中的哪个位置。

先讲评估范围：
系统级评估一般用于汇总整体运行表现，宏观展现系统整体状况。
组件级评估则用于定位单个问题的根源。
举例：监测整套系统延迟时发现延迟过高，想要定位故障源头，就需要依靠组件级评估，排查问题究竟出在检索器、大模型还是其他组件上。

评估主体类型用来区分评估结果的产生方式。
基于代码的评估：成本最低、逻辑最简单、落地便捷。
场景包含统计系统每秒处理提问数量、编写单元测试校验大模型是否输出合规 JSON 格式内容等。
这类评估可自动执行、结果确定可复现，运行成本几乎可以忽略不计。

与之相对的是人工反馈与人工评估。最常见的形式就是用户对回答点赞或点踩。
即便这类反馈无法提供详细信息，但差评数量增多本身就是系统存在故障的有效信号。
你也可以增设文本输入框，收集用户的详细评价。
还有一类评估可全自动运行，但前期需要人工介入：由工作人员预先构建「提问 + 预期检索文档」的测试数据集。数据集构建完成后，就能快速计算精确率、召回率等常规指标。但要注意，初始测试数据集必须依靠人工制作。

总体而言，人工标注反馈的成本更高，但能够捕捉到代码评估无法识别的问题。

大模型充当裁判（LLM as a judge）是折中方案：利用语言模型对系统各个组件的表现打分。
例如交由大模型判断检索器召回的文档是否和用户提问相关。
该方案比代码评估更加灵活，同时成本低于人工评估。
不过充当裁判的大模型也需要精心调校：模型本身存在偏见，可能偏爱同系列模型生成的回答。
同时必须为其制定清晰评判规则，相比 0 至 100 分的连续打分模式，设置「相关 / 无关」这类离散判定标准时，评判效果更佳。

接下来我们把上述各类评估思路整合起来，搭建一套精简且完备的指标采集方案。
初期建议采集每一个核心组件以及整套系统的软件性能指标、质量指标。
延迟、吞吐量、内存占用、每秒生成 token 数这类系统性能指标属于代码式评估，采集成本低廉、实现简单，组件层面与系统层面均可轻松采集。

而质量指标，通常需要结合人工标注或者大模型裁判模式。
系统整体质量指标：开放点赞、点踩功能收集用户反馈，以此判断整体回答质量。
检索器评估：人工标注构建「提问 + 目标检索文档」测试集，计算召回率、精确率。
大模型效果评估：采用 RAGAS 这类基于大模型的评估工具，评测回答相关性、引用质量、模型屏蔽无关检索内容的能力等。

这套方案既能掌握整套系统与各个组件的性能、质量状态，也兼顾了低成本的延迟监测指标，以及依靠人工标注、模型调用实现的高价值质量指标。后续你可以按需拓展更多观测方向。

以上就是 RAG 可观测系统的组成结构与设计取舍的简要介绍。下一课时我们深入落地搭建这套系统时需要考虑的各类要点。

## 日志记录，监控与可观测性

确定好需要采集哪些 RAG 系统指标之后，就要搭建对应的系统来采集这些数据。
下面介绍几种可用于搭建可观测体系的工具。

市面上存在大量面向大模型应用的可观测平台，这类平台原生支持各类常规评估任务：采集系统级、组件级指标、记录系统流量、支持针对系统新配置开展对照实验。
使用这类平台，你无需耗费大量精力从零设计、搭建可观测系统，能够把更多精力投入监控 RAG 运行表现、尝试优化方案。

我们以开源可观测评估平台 **Phoenix**（由 Arize 公司开发）举例，该平台内置多款工具用于评测 RAG 系统性能，先介绍其中最常用的链路追踪（traces）功能。

链路追踪可以完整追踪一条提问在整条 RAG 链路中的流转全过程，查看系统内每个组件对这条提问的处理与改动。
举例来说，你可以查看原始提问文本、发送给检索器的查询语句、检索器返回的文本块、重排模型对文本块的处理过程、最终送入核心大模型的完整提示词，以及模型生成的最终回答。
链路还会记录每一个步骤的延迟等关键信息。

无论是处于早期原型阶段还是已经上线生产，链路追踪都是排查 RAG 问题的常用手段。
例如某条提问最终回答效果很差，你就能追溯整条处理链路，定位故障究竟发生在哪一个环节。

Phoenix 平台还可以便捷接入本章节前面讲到的各类评估方案，比如它支持对接 RAGAS 评估库。
因此你想要计算检索结果的相关性、核验大模型引用来源是否准确时，只需简单接入即可新增对应的评估流程。

搭建好基础评估链路后，就可以开展简易实验。
你可以反复输入自定义提问，观测整条 RAG 链路如何处理该问题；也可以对系统改动进行 A/B 测试，观测改动对系统性能带来的影响。
借助这些功能，就能判断新版系统提示词是否真正提升了回答质量，或是新增重排模块能够带来多大的性能提升。

链路追踪提供底层细节数据，同时你通常还需要宏观聚合统计数据来监控整体运行状态。
Phoenix 能够生成关键指标日报，涵盖检索器准确率、模型幻觉率等数据。

尽管 Phoenix 以及其他大模型可观测平台基本可以覆盖 RAG 绝大部分评估需求，但依旧存在部分能力缺口。
比如它并不擅长监控向量数据库的算力与内存占用情况。

遇到这类场景，可以搭配 Datadog、Grafana 这类传统监控观测工具一起使用。

一套完善的可观测链路最终会形成系统优化的正向飞轮：
观测系统处理真实线上流量的表现，找出系统漏洞与优化方向，再验证优化改动带来的效果。
长期迭代下来，就能逐一调优各个组件，让整套系统适配用户真实的使用习惯。
该流程里有一项实用能力：基于 RAG 过往处理过的用户提问，构建自定义测试数据集。
留存这些历史提问并重新送入系统运行，就能验证系统改动，对真实线上用户提问的处理效果产生了何种影响。

下一课时，我们讲解如何构建这类自定义测试数据集。

## 定制化评估

基于系统过往接收的提问构建自定义数据集，既能深入复盘系统历史运行表现，还可以开展对照实验，验证系统重构后，在真实用户提问场景下性能会产生何种变化。

下面讲解搭建这类数据集的方法。
自定义数据集本质上就是系统曾经处理过的所有提问集合，再按需存入每条提问在 RAG 系统中完整流转过程的各类数据。
你可以只留存用户原始提问与系统最终回复；也可以存入大量额外信息，例如向量数据库检索到的文档、重排模型处理前后文档的排序结果、查询改写模块的输出内容等等。

正因具备极高灵活性，搭建自定义数据集时，核心决策就是确定需要存储哪些数据。简单的判断原则：存储你后续想要评估所必需的数据。
举例来说，几乎必然需要保存用户输入的原始提问、RAG 系统生成的最终回答。仅凭这两项基础数据就能大致判断系统表现，还可以观测修改提示词之后，回答内容发生了哪些变化。

但仅依靠这些信息，只能完成端到端整体评估。倘若想要做组件级评估，判断检索器、重排模块、查询改写模块各自的运行效果，就必须保存每个组件的输入与输出数据。
通常我们都会完整记录组件每一步运行细节，因此用于记录 RAG 调用日志的数据表很容易拥有数十个字段，存储内容涵盖发起提问的用户 ID、重排模型筛选过的文本片段、智能体工作流里各个路由大模型的输出结果等全部信息。

留存如此丰富的数据，便可单独分析系统每一个组件，从多个维度评测整体性能。
举个例子，如果你搭建的是客服对话机器人，可以按照问题主题做筛选，进而发现：退款相关问题的回复质量很好，但关于商品发货延迟的问题，系统回答效果极差。

接着排查发货延迟类提问回答质量差的原因，通过日志分析就能发现：检索器很难检索到和这类问题相关的文档，这时你就需要往知识库中补充更多相关资料。
只要搭建完善的可观测体系，就能及时发现问题、精准定位根源，并且验证优化方案是否生效。

分享一段我从业经历中的真实案例：我曾负责一套专用 RAG 系统，该系统支持生成文本、图片，还可借助 Mermaid.js 生成代码图表。后续不断收到用户反馈，系统生成的部分图表质量很差。
我们顺着日志逆向排查，发现大部分故障场景都发生在用户要求绘制图表时：路由大模型错误理解用户指令，将绘图请求转发给了文生图模型。这类模型擅长生成人物、实物图片，却并不擅长制作图表。

找到问题根源后，我们修改了路由大模型的系统提示词，让绘图类请求交由代码生成模块制作图表，不再调用文生图模型。
得益于完善的监控与日志体系，在收到用户问题反馈后，我们快速定位故障成因，并迅速上线修复方案。

有时你需要像上面案例一样，逐个排查表现糟糕的单条提问；而当日志数据体量庞大后，往往还需要对数据做可视化处理，以此挖掘整套系统或各个组件性能的宏观趋势。
比如，将系统接收的全部用户提问可视化，再借助聚类算法归纳出用户咨询的各大主题，像是新品发布、故障排查类问题。
区分不同类型的提问之后，你就能单独针对某一类问题运行评估链路，检测系统是否在特定题型上存在性能短板。

自定义数据集是优化 RAG 应用、适配真实用户提问习惯的重要工具。将自定义数据集融入系统评估流程，是优化系统应对真实用户提问能力的最优方式。

## 量化

当你能够评测 RAG 系统、并且针对不同配置开展对照实验后，就要面对所有软件项目都会遇到的经典取舍问题：成本、速度、质量三者的平衡。后续课时我们会讲解这三者的权衡方案，在此之前先介绍一个核心概念：**量化（quantization）**。

简单来说，量化是针对大语言模型、嵌入模型生成向量的压缩技术。量化会把大模型内部权重、嵌入向量的数值替换为精度更低的压缩数据类型。
经过量化后的模型与向量体积更小、运行成本更低、速度更快，大多数情况下检索相关性、回答质量并不会出现明显衰减。

我们用类比来理解量化原理：量化和图片压缩逻辑一致。
一张高清图片每个像素色彩占用 24 bit 数据，色彩效果优秀，但存储开销很大。
如果将每个像素改用 12 bit 甚至 6 bit 存储来压缩图片，压缩后的体积分别变为原图的 1/2、1/4，能够大幅节省存储空间。
但代价是：12 比特的图片画质已经下降，6 比特图片会出现明显色彩噪点。
不过根据图片使用场景不同，用小幅画质损耗换取大量内存节省，往往是划算的。

量化对大模型与嵌入向量采用了完全相同的思路：以轻微质量损耗为代价缩小体积。
先讲大模型的量化原理：常规语言模型的单个参数占用 16 bit 内存。
现代大模型参数量普遍在十亿至万亿级别，体积庞大，存储需要海量内存，运行依赖高性能显卡。
量化可以把 16 bit 的模型参数压缩至 8 bit 甚至 4 bit，大幅降低运行所需显存，代价仅为模型性能、输出质量轻微下降。

嵌入向量的量化逻辑同理。常见的 768 维向量由 768 个 32 位浮点数组成，知识库内单条向量就要占用 3KB 空间；更高维度向量的占用空间更是数倍于此。
一旦向量规模达到百万乃至数十亿级别，整体存储体量十分庞大。向量需要加载至昂贵的内存中才能实现高速向量检索。
整型量化是压缩向量的主流方案：把 32 位浮点数替换成体积更小的整型（例如 8 位整型），向量体积直接缩减为原本的 1/4，存储空间大幅节省，并且整型数值的计算效率极高。

整型量化具体流程：

1. 找出向量每一维数值的最大值与最小值，确定该维度数值的取值区间；
2. 将这个区间均匀划分为 256 段（8 bit 刚好可以表达 0~255 共 256 种独立数值），分段编号 0、1、2……255；
3. 原始向量里每一个浮点数，根据所处分段对应一个整型编号；
4. 只需要额外保存该维度最小值、每段区间宽度，后续就能凭借 8 bit 整型反向近似还原出原始 32 位浮点数。

尽管只用 1/4 的数据量、算法原理简单，但 8 位整型量化的实际表现十分优秀。在召回率 @k 这类基准测试中，量化后召回率通常仅下跌数个百分点。
量化后的嵌入向量既能减少向量数据库存储压力，又能简化计算逻辑、加快检索速度。
经过量化的大模型，在通用基准测试里性能降幅同样很小，还能减少显存占用、提升文本生成速度。
简言之：仅牺牲少量质量，就能换来内存占用下降、运行速度提升两大收益。

8 位整型向量量化已是通用方案，如今 1 比特（二进制）量化向量也逐渐普及。
该方案将向量每一维从 32 bit 压缩至 1 bit，整体体积直接缩小至原先的 1/32，压缩幅度极大。
在这种极致压缩模式下，向量每一维的值只有 0 和 1，仅用于标记该维度原始数值为正数或是负数。
可想而知，如此高强度压缩后，基于嵌入模型的检索性能会出现明显下滑。
但二进制量化能极大缩小向量体积、成倍加快检索速度，还可以搭配其他技术组合使用：
先用 1 比特量化向量完成快速粗召回，再使用完整 32 位原始向量做重打分。

另一种向量压缩方案是**套娃嵌入模型（Matryoshka embedding model，Matryoshka 源自俄语套娃一词）**。
这类向量的特性是：做相似度对比时，可以只截取向量其中一部分维度参与计算。
举例：完整向量共 1000 维，你可以只取前 500 维、前 100 维参与运算。
想要实现该特性，套娃嵌入模型拥有特殊结构：向量维度按照信息密度排序。
此处的信息，指大批量文本向量化后，该维度数值的统计方差大小。
普通嵌入模型各个维度的方差、信息量基本均等；
而套娃模型经过特殊训练，靠前维度方差更大、承载的信息量更多，靠后维度方差小、信息占比低，舍弃后造成的精度损失微乎其微。

套娃向量有两种典型用法：

1. 始终只用前 100 维做检索，节省存储空间、加快运算速度，同时尽可能保留有效信息；
2. 先用前 100 维完成初次召回，再从低速低成本存储介质中取出剩余 900 维，拼接成完整 1000 维向量，对初次召回的文档集合重打分。

套娃模型灵活的特性，非常适合需要在低精度、高精度向量模式之间快速切换的动态业务场景。

以上是前沿量化技术拓展内容，核心结论为：你应当尝试使用整型量化后的大模型与嵌入模型。
绝大多数大模型、嵌入模型厂商，都会在原版基座模型之外，同步推出 8 bit、4 bit 量化版本。
量化带来的存储空间、部署成本缩减效果显著，而质量损耗非常微弱。

## 专业名词注释

1. Quantization 量化：降低模型权重 / 向量数值精度实现压缩加速
2. Matryoshka embedding 套娃嵌入：维度按信息量排序，可截断部分维度使用
3. Binary quantization 1 比特二进制量化：仅区分正负，极致压缩
4. Recall@k：取前 k 条检索结果时的召回率，检索核心评估指标。

## 成本vs响应质量

接下来聊聊所有工程师都关心的话题：成本预算。

在搭建初代 RAG 系统时，你大概率只会专注探索可行方案、做出可运行的原型版本。可当系统扩容至承接数百、数千乃至百万级请求时，成本控制就变得愈发关键。
下面介绍几种优化方案，在保障回复质量的前提下控制系统开销。
常规 RAG 应用中，两大主要成本来源分别是**向量数据库**与**大语言模型**。我们先讲解如何管控大模型成本。

## 大模型降本方案

1. **选用体量更小的模型**
    
    无论是负责生成最终回答的核心大模型，还是智能体系统里的路由模型，换成体积更小、价格更低的模型，往往也能实现相近的整体效果。
    
    小型模型分为两种：原生参数量更低的模型；或是将参数量化为 8 比特等低精度格式的模型。
    
    尤其是大模型只承担有限任务时，小模型的表现常会超出预期。对小型模型做微调，就能低成本实现不错的效果。
    
2. **控制输入、输出 Token 总量**
    
    RAG 的提示词很容易变得冗长，尤其是单次检索返回大量长文本片段时。
    
    可以适当减少检索文档数量，也就是调低 Top-K 取值。
    
    多数大模型生成内容容易啰嗦，而平台计费是按照生成的每一个 Token 收费。
    
    优化系统提示词引导模型精简输出、设定严格的生成 Token 上限，也是简单有效的省钱手段。
    

无论是缩减模型体积还是缩短提示词长度，完备的可观测链路必不可少：用来评估改动带来的影响，判断「省下的成本」是否值得换取「小幅下降的回答质量」。

3. **私有化部署大模型专用硬件**
    
    Together AI、亚马逊云、谷歌等云厂商提供的云端大模型推理接口，非常适合原型开发阶段。
    
    但当业务扩容至数万、百万级请求规模后，可以租用同厂商的专属硬件部署模型进一步省钱。
    
    专属推理节点还有额外优势：硬件资源仅供自身业务流量使用，稳定性更强。
    
    专属硬件部署按照显卡运行时长计费，规模化部署后，按时计费的模式对比按 Token 计费，能省下巨额开支。

## 向量数据库降本方案

想要缩减向量数据库开销，首先要了解向量数据库常用的三类存储介质：内存（RAM）、磁盘、云端对象存储。

- 内存：速度最快、单价最高
- 云端对象存储：速度最慢、成本最低
- 磁盘：性能与成本介于两者之间

内存每 GB 的价格通常是磁盘的数倍，磁盘单价又数倍于对象存储。
省钱的核心逻辑：只把能真正提升系统性能的数据存放在高速高价存储中。
举例：HNSW 索引必须放入内存，保障向量检索速度；但文档正文无需存入内存。
可以把高频访问的文档存入磁盘，极少访问的数据放到廉价云端对象存储。
不少向量数据库自带配套监控功能，还能根据业务需求自动在不同存储介质之间迁移数据。

典型落地方式：**多租户架构**，按照所属用户 / 企业划分向量库内的文档。
假设向量库中有 100 万份文档，分属 1000 位不同用户，每位用户仅可访问自身文档，那么可为每位用户单独建立专属 HNSW 索引。
该架构可以做到按需把租户数据加载至高价高速内存：比如用户登录网站时，再将其向量载入内存；欧洲租户的数据在欧洲夜间时段，默认存放至低速存储。
全程只按需在高价内存中读写数据，基于租户隔离的架构可以高效完成这套调度逻辑。

## 优化核心思想

所有优化手段的本质逻辑一致：工程师需要理清成本产生的源头，确认每一笔开销都能对应匹配的性能收益。

- 大模型降本：更换小模型、精简提示词
- 向量数据库降本：减少高价存储的数据占用量，在内存、磁盘、对象存储之间灵活调度数据

所有优化改动都需要配合实验与性能监控，以此判断节约的成本是否值得牺牲部分性能。

## 延迟vs响应质量

生产环境下部署 RAG 应用，还需要做好一项重要权衡：单次查询耗时（延迟）与回答质量之间的取舍。
仅仅在系统中接入检索模块就会带来额外延迟；而如果你不断新增模块来提升回答质量（例如重排模块、结构更复杂的智能体系统），延迟还会持续升高。下面深入分析这组取舍关系，以及如何为系统找到平衡点。

延迟的重要程度，完全取决于系统的使用场景。
电商网站的用户对响应迟缓容忍度极低，因此商品推荐系统通常会优先压低延迟，即便牺牲推荐精准度、没法选出全站最合适的商品也在所不惜。
反过来，用于辅助医生诊断罕见病的 RAG 系统，则会优先保障回答质量，哪怕生成答案需要耗费更长时间。

想要解决延迟问题，可以记住一条核心规律：绝大部分延迟都来源于 Transformer 模型的运算过程，因此**最大的延迟来源就是调用大语言模型**。
检索环节带来的延迟其实很低；即便包含基于 Transformer 的重排步骤，现代数据库（尤其是向量数据库）本身速度很快，并且具备优秀的扩容能力。
想要降低延迟，优先优化核心大模型环节即可。

## 优化核心大模型以降低延迟

1. **改用更小的模型**
    
    在硬件与内存条件一致的前提下，小参数量大模型、量化后的模型运行速度必然更快。
    
2. **增设路由小模型做动态分流**
    
    部署一个轻量化路由模型，作用是读取用户提问，判断该问题适合交由大模型还是小模型处理：
    
    复杂推理类问题分发至性能更强的大模型；简单问题交给轻量化高速模型。
    
    如此一来，简单提问的延迟可以被控制在低位，只有真正需要深度推理的复杂问题，才允许产生更高延迟。
    
3. **缓存机制提速（高频相似问题场景）**
    
    针对频繁出现的用户提问，缓存问题对应的完整回答。
    
    收到新提问时，快速计算该提问与缓存库内问题的相似度；如果命中高度相似的历史问题，直接返回缓存答案，省去耗时的模型生成流程。
    
    合理调优缓存规则后，可以大幅优化大部分请求的延迟表现。
    
    如果既想用缓存提速、又希望回答带有一定个性化效果，可以取出缓存答案后，送入一个轻量高速小模型做微调润色，让回答贴合本次用户提问。
    

## 优化链路里其余 Transformer 组件

完成核心大模型延迟优化后，再处理链路中其余基于 Transformer 的模块，例如查询改写器、重排器、路由模型等。
这些模块各司其职，但都会增加延迟。
建议做法：统计每个组件新增的延迟时长，同时统计该组件带来的回答质量增益。
举例来说，你可能会发现查询改写模块带来的质量提升微乎其微，这时就可以直接移除该组件。

## 优化检索环节延迟

虽然模型生成是延迟的主要来源，但依然有手段削减检索阶段耗时：

1. 在向量数据库中使用二进制量化嵌入向量，简化向量距离的计算逻辑，加快检索速度；
2. 当向量数据库体量庞大时，采用分片（Sharding）拆分至多个实例，降低单次检索耗时。这是各类通用数据库优化延迟的通用方案，绝大多数向量数据库厂商都配套了分片落地工具。

## 整体优化步骤总结

RAG 系统几乎永远存在「延迟 ↔ 质量」的取舍关系，优化流程遵循固定顺序：

1. 先明确业务能够容忍的最大延迟；
2. 如需降延迟，优先优化核心大模型；
3. 再处理链路中其他基于大模型 / Transformer 的功能模块；
4. 若延迟依旧超标，再优化检索等其余链路组件。

依托完善的可观测系统，你可以直观看到每一轮优化带来的变化，迭代式把延迟降到项目要求的标准。

## 安全性

下面我们聊聊 RAG 应用的安全防护。
网络安全是一门深奥且持续迭代的领域，无法穷尽所有安全风险。
因此我们只聚焦 RAG 系统独有的安全风险与防护方案，核心重点是保护知识库内的数据安全。

企业搭建 RAG 系统的一大核心原因，就是要对内处理私有、涉密专有数据。
这些资料特意不放到公网（避免被大模型训练收录），即便建成 RAG 系统后，通常也要求数据持续保密。
知识库的数据存在几种泄露途径：

## 泄露途径一：用户通过提问诱导数据外泄

用户精心构造提示词，就能诱导大模型直接引用检索出来的知识库片段内容。
即便部署了防护机制，应用使用者依然存在间接获取知识库内容的可能性。

对应的防护方案：

1. **匹配权限的用户身份认证**
    
    如果知识库存放企业内部私密数据，最基础的防护手段就是仅允许已登录的企业员工调用 RAG 系统。
    
2. **基于 RBAC 角色权限做多租户隔离存储**
    
    用户发起检索请求时，只能调取自身角色权限范围内的文档。
    理论上可以把所有文档放在同一个租户内，依靠元数据过滤实现权限管控，但这种方式极易出现权限漏洞。
    元数据筛选更适合做个性化业务，不能当作安全手段。
    想要保障安全，采用相互独立存储的多租户架构会稳妥得多。

## 泄露途径二：调用公有大模型服务商接口引发泄密

当你把拼接了知识库检索片段的完整提示词发给第三方大模型厂商生成回答时，这些私密数据就脱离了你的管控范围。
如果知识库涉密等级较高，该风险无法接受。

解决办法：**全链路本地化私有化部署**
把大模型、向量数据库全部部署在自有机房硬件上。
这套方案会增加项目复杂度与成本，但整条 RAG 链路的知识库数据全程由你掌控。
如果业务既要搭建 RAG，又必须严格保障知识库安全，全本地化部署值得采用。

## 泄露途径三：向量数据库被黑客入侵窃取数据

向量数据库和传统数据库一样，存在被攻破入侵的风险。
传统数据库的防护手段是加密存储数据：即便黑客拿到数据库文件，也无法直接读取加密内容。
但向量数据库有特殊的安全难点：
ANN 近似近邻检索算法正常运行的前提是，文档稠密向量必须解密后加载至内存中。
文档文本片段可以加密存储、检索完成后再解密拼接提示词，不少向量数据库厂商已经内置该能力，你也可以自行实现片段加解密逻辑。
该方案会增加系统复杂度、小幅提升延迟，但能多一层安全保障。

然而，存放在内存中未加密的稠密向量依旧存在安全隐患：现有研究证明，黑客可以凭借稠密向量反向还原出原始文本。
也就是说，就算文档片段做了加密，黑客拿到明文向量后，依旧有可能还原出原文。
业界正在研究对应的解决手段：给稠密向量添加噪声、对向量做变换处理、在保留向量距离特性的前提下降维（隐藏原始语义）。
但这些方案都会增加检索模块复杂度，并且大概率会造成性能下降。

黑客想要完成向量还原攻击，需要直接入侵数据库，还要借助尚处于实验阶段的向量还原技术，虽有可行性，但属于小众攻击方式，了解该风险即可。

## 总结

以上是 RAG 特有的安全问题简述，核心要点：
你的知识库大概率包含私密数据，必须管控、限制数据的访问途径。
将上文 RAG 专属防护手段，搭配通用网络安全防护体系，就能大幅提升生产环境 RAG 系统的安全性。

## 关键名词注释

1. RBAC：基于角色的访问控制
2. 多租户隔离：不同用户 / 组织的数据分开存储，权限相互隔离
3. ANN：近似最近邻检索，向量数据库核心检索算法
4. On-premises：本地机房私有化部署

## 多模态检索增强生成

本课程前面讲解的 RAG 系统全部基于文本数据搭建，但如今信息的存储格式多种多样：幻灯片、PDF、图片里都蕴含着有价值的信息，我们希望把这些内容纳入知识库，供给大模型调用。得益于多模态模型的前沿发展，如今搭建能够处理各类数据格式的 RAG 系统已经逐步落地。下面介绍它的实现原理。

多模态模型能够处理多种类型的数据，最常见的组合是文本 + 图像，同时也支持音频、视频。
一套典型的多模态 RAG 具备这些能力：支持图文混合提问、知识库同时存储文本与图片文件、最终输出文本形式的回答。
想要实现以上能力，检索器与大模型都必须升级为多模态版本，接下来分别说明各个组件需要做出的改动。

## 一、向量数据库的嵌入模型升级为多模态嵌入模型

多模态嵌入模型可以将多种格式的数据映射至**同一个向量空间**。
和纯文本嵌入模型逻辑一致：用该模型分别对单词 dog（狗）、puppy（幼犬）做向量化，二者向量在空间中距离很近；
如果输入一张狗狗的图片，这张图片生成的向量同样会落在该区域附近。
同理，单词 tree（树木）和树木图片对应的向量位置相邻，但处于向量空间的另一区域。
简言之：多模态嵌入模型遵循和文本嵌入完全一致的规则，语义相近的内容向量相互靠近，区别只是它兼容多种模态的数据。

拥有多模态嵌入模型之后，向量检索流程和传统文本 RAG 基本一致：

1. 将知识库内的图片、文本全部向量化，存入同一向量空间；
2. 用户发来提问（无论是文字还是图片），使用同一个多模态嵌入模型完成向量化；
3. 执行常规向量检索，召回向量相似度最高的图片或文档片段；
4. 把检索得到的图文内容拼接到提示词中，送入大模型。

## 二、将大模型替换为图文大模型（Language Vision Model）

想要让大模型同时读取文本与图片，需要使用图文大模型。
这类模型的运行逻辑和纯文本大模型大体一致，但新增了图片编码能力：图片会被拆解为多个图像块（patch），每一个图像块被转换成独立的 Token。
根据分辨率不同，一张图片大约可以转换成 100～1000 个 Token。
核心关键点不在于图片占用多少 Token，而是图文都可以被转化为 Token 序列，和纯文本模型的输入形式对齐。

图文大模型的工作流程：把图文混合的 Token 序列送入 Transformer 结构，精准理解提示词里文本、图片以及彼此之间的关联关系，最终输出文本 Token 完成作答。

只要配齐多模态嵌入模型与图文大模型，就能很轻松地把原有 RAG 升级成可存储图文知识库的版本，整体架构基本不变，只是新增了图像处理能力。

## 三、多模态 RAG 的优势：兼容幻灯片、PDF 等常见文件

RAG 新增图片处理能力后，便能接入大量可以转为图片的常用文件，幻灯片、PDF 都可以直接当成图片处理。
但这类文件存在难点：单页 PDF 或幻灯片信息密度极高，同一页面里混杂文字、图表、配图、注释。
只用单个向量很难完整承载一页 PDF 的全部细节，因此图片也需要像文本一样做分片（Chunk）处理。

### 传统 PDF 分片方案

借助复杂算法识别 PDF 页面布局，区分图表、图片、文字区域再分别切片。
缺点：算法容易识别出错，稳定性差。

### 新式方案：PDF RAG 网格切分

不做布局识别，直接将每一页页面均匀切分为正方形网格区块，每个区块单独用多模态模型生成稠密向量。
一页文档会生成上千条向量而非单独一条向量，检索逻辑近似 ColBERT：提问里的每个文本词，分别匹配页面中最合适的网格区块，累加所有匹配分数得到整页文档的匹配分值。
该方案通用性极强，任意图片都可以网格拆分，检索效果出色，是多模态检索极具前景的方向。
唯一弊端：向量数量暴增，会给向量数据库带来巨大存储压力。
目前各大向量数据库厂商都在陆续适配该类多模态检索能力，未来搭建多模态知识库 RAG 的门槛会持续降低。

## 四、行业现状总结

多模态 RAG 仍处于前沿高速发展阶段。
绝大多数大模型厂商都推出了图文大模型，但多模态嵌入模型大多还处在实验阶段。
如果你想要拓展 RAG 系统的能力边界，后续多模态 RAG 领域还会持续迎来大量技术突破。

## 专业术语注解

1. Multimodal embedding 多模态嵌入：图文等不同模态数据映射至同一个向量空间
2. Language Vision Model 图文大模型：可解析图片 + 文本的大模型
3. Patch 图像块：图片切分后的基础单元，用来编码成图像 Token
4. PDF RAG Grid Split PDF 网格分片：不分布局、均匀切分页面做细粒度检索
5. ColBERT：细粒度词级匹配检索架构

#### Blocker

##### RV-001 · 共享发起能力互相矛盾

- **问题**：§5.2 规定 editor 不能管理授权，§7 仅允许拥有共享能力的用户发起授权；但 §8.1 又定义“普通 editor/member 发起共享”并进入审批。当前无法判断 editor/member 能否发起共享，viewer 是否可以发起也未明确。
- **影响**：共享入口、角色能力矩阵及审批触发条件无法唯一设计。
- **选项**：A. 仅 manager 可发起共享；B. editor/member 可发起共享申请，manager 可发起直接生效或需审批的共享，viewer 不可发起；C. 单独建立“发起申请”和“直接管理授权”两套能力矩阵。
- **推荐**：B。保留默认审批策略的业务价值，并明确申请权不等于授权管理权。
- **需要用户决定**：是。
- **用户决策**： 这里说的共享 应该指的是knowledgebase， knowledgebase的共享只有Organization的admin或者部门负责人，或者project负责人才可以进行共享知识库并可以指定其权限，document若上传到本门或者项目知识库，需要由部门/project负责人审核后 才能进行处理。个人知识库则不需要任何审批

##### RV-002 · 退出 Organization 后 User 直授权是否失效未定义

- **问题**：§7 只说明退出 Organization 后失去组织、部门和项目路径权限，没有覆盖 User 直授权；同时文档允许跨组织共享，User 直授权是否依赖目标 Organization 成员身份不明确。
- **影响**：同一退出场景可能得到继续访问或立即失权两种相反结果，属于隔离边界问题。
- **选项**：A. 退出目标 Organization 后，包括 User 直授权在内的全部该组织资源权限失效；B. User 直授权独立于成员关系，退出后仍有效；C. 本组织成员退出时直授权失效，跨组织直授权另设规则。
- **推荐**：A。与 Organization 默认隔离边界一致，规则最安全、最容易解释。
- **需要用户决定**：是。
- **用户决策**： A，退出Organization后，该Organization的所有资源都失效，退出department/project相应的知识库也没了。另外个人知识库也是属于Organization， 退出Organization后，个人知识库也没有了

#### Major

##### RV-003 · 核心实体状态模型不闭合

- **问题**：Organization、KnowledgeBase 和 Department 缺少完整状态枚举；User、Project 虽有状态名称，但没有合法转换、操作主体和转换结果。
- **影响**：后台状态操作、授权有效性及审计前后值会产生不同实现。
- **选项**：A. 当前版本补齐全部实体的状态与转换；B. 只补齐会影响访问的最小状态和转换，其余后续版本扩展；C. 删除当前没有明确行为的状态。
- **推荐**：B。先闭合首版访问治理所依赖的状态行为。
- **需要用户决定**：是。
- **用户决策**： A， 补齐所有

##### RV-004 · “敏感 Document”没有判定与维护规则

- **问题**：§8.1 对敏感 Document 设置审批规则，但没有定义敏感属性、标记方式或谁能设置和取消。
- **影响**：该审批策略无法触发，也无法设计对应管理任务。
- **选项**：A. 增加 Document 级敏感标记及其管理权限；B. 改为 KnowledgeBase 级敏感属性；C. v0.1 删除敏感资源特例。
- **推荐**：A。与当前按 Document 审批的规则一致。
- **需要用户决定**：是。
-  **用户决策**： A，没有敏感Document 这一说法

##### RV-005 · Project“关联知识库”与“获得授权”含义混淆

- **问题**：§4、§5.1 同时使用“关联”和“授权”，但只明确授权产生访问，未说明关联是否带来可见性或其他产品行为。
- **影响**：可能被设计成纯元数据关系，也可能被误解为访问路径。
- **选项**：A. 明确关联仅用于业务归类和展示，不产生任何访问权限；B. 删除关联，只保留授权；C. 定义关联产生的独立可见范围。
- **推荐**：A。保留项目与知识资产的业务关系，同时不破坏授权模型。
- **需要用户决定**：是。
- **用户决策**：B 只保留授权吧，KnowledgeBase可通过相应的负责人，或者平台Admin授权给project，部门负责人可以把本部门的KnowledgeBase授权给guest或者其他人物属性并给他权限

##### RV-006 · blocked 覆盖规则与已确认决定不一致

- **问题**：§6 写“Document 直授权默认不能反向解除 KnowledgeBase blocked”，“默认”暗示存在例外；但 `需求记录.md` 已确认“不能被文档直授权反向解除”。此外 blocked 作为可授予级别和显式拒绝规则之间的关系尚未说明。
- **影响**：权限计算可能产生相反结果，且正文偏离已确认决定。
- **选项**：A. 删除“默认”，明确任何 Document 直授权都不能覆盖 KnowledgeBase blocked，并定义 blocked 的作用主体；B. 保留例外并定义可解除的角色与流程；C. 仅支持 Document blocked，不支持 KnowledgeBase blocked。
- **推荐**：A。忠实落实已确认决定。
- **需要用户决定**：否，可按既有决定修正文案；涉及 blocked 作用主体时仍需确认。
- **用户决策**：Document在平台上应该是有专门的文档管理平台， 可按层级进行管理，也可以独属于某个部门，例如一级部门上传一个文档，可以共享给所有二级部门，类似于下发通知，也可以只在一级上传该文档的部门使用，再例如，Organization的Organization级考核办法这些就应该是全Organization共享的。这是Document的权限，再者能看到该Document的user，且对某个知识库有editor权限，则可以将Document加入到该知识库中，当然也需要这个知识库所属的部门/项目负责人审核。加入后，该Document将进行浅拷贝，此时若Document被上传者删除，也不会影响知识库中的Document，此时的Document会存在于使用该Document的知识库所对应的部门/项目中(这说的是文档管理平台， 也就是有文档管理平台和知识库管理平台)

##### RV-007 · external member 与 Organization guest 的边界不清

- **问题**：§4 允许其他组织用户直接作为 external member 加入 Project，但未说明是否必须先成为目标 Organization 的 guest/member；§2.3 也没有定义 guest 的最小能力。
- **影响**：跨组织项目的加入流程、成员管理入口和资源边界无法唯一确定。
- **选项**：A. external member 只需平台账号，不需要目标组织成员身份；B. 必须先成为目标 Organization guest；C. 两种方式都支持，但权限来源和管理方式分开。
- **推荐**：A。与“直接作为 external member 加入 Project”的现有措辞一致。
- **需要用户决定**：是。
- **用户决策**：A

##### RV-008 · 审批状态的异常与终止分支不完整

- **问题**：§8.2 未定义谁能取消、何时过期、pending 时资源失效或主体退出的结果，以及 rejected 后能否重新发起。
- **影响**：审批中心无法稳定表达当前步骤、可执行操作和最终结果。
- **选项**：A. 补齐完整审批状态机；B. v0.1 采用最小规则：发起人可取消、有效期或策略触发过期、资源或主体失效自动取消、驳回后可重新申请；C. v0.1 只保留 approved/rejected。
- **推荐**：B。足以闭合首版流程且控制范围。
- **需要用户决定**：是。
- **用户决策**：开源版本不要搞这么复杂，不定义取消，过期，就一条简单线路就可以了，发起审批，负责人审批通过/不通过;发起人也可以在负责人没有审批的时候取消掉

##### RV-010 · 权限查询的可查询对象范围未定义

- **问题**：§5.3、§9 只规定查询有效能力，没有说明普通用户能否查询他人权限，或仅管理员可按管理范围查询。
- **影响**：可能造成越权查看成员关系或权限来源。
- **选项**：A. 普通用户只查本人，管理员按治理范围查主体；B. 只有管理员可使用权限查询；C. 所有组织成员可查组织内主体。
- **推荐**：A。兼顾自助解释和隐私边界。
- **需要用户决定**：是。
- **用户决策**：开源版本先按照, 普通用户只查本人， 平台admin可以查所有，但项目/部门的负责人可以查看所拥有知识库，这个知识库有哪些人在使用，每个人都有什么权限，然后个人知识库也可以授权给其他人使用，也能查看个人知识库有哪些人在使用，每个人有什么权限，另外关于文档平台，每个人可以查看该人隶属的项目、部门，其他部门下放权限共享的文档，另外关于文档管理平台和知识库管理平台这块和user交互的权限应该细化一下

##### RV-011 · 审计事件与“高风险操作”边界不够明确

- **问题**：§10 使用“至少”列举审计事件，§9 又使用未定义的“高风险操作历史”，两者没有统一口径。
- **影响**：首版审计范围和验收边界不清。
- **推荐**：把首版必须审计事件列为明确基线，并定义哪些操作属于高风险。
- **需要用户决定**：否，可按现有事件清单整理。
- **用户决策**：开源版本 不要搞这么复杂， 就一条简单线路就可以了，发起审批，负责人审批通过/不通过;发起人也可以在负责人没有审批的时候取消掉

##### RV-012 · 部分实现约束应改写为用户可观察的安全结果

- **问题**：§11、§12 中的客户端可信字段和检索执行顺序偏实现表达。
- **影响**：容易让需求稿承担技术设计职责，且不利于产品验收。
- **推荐**：保留安全红线，但补充或改写为“未授权内容不会被检索、展示或进入模型上下文”等可验证结果。
- **需要用户决定**：否。

##### RV-013 · 平台级 Admin 自身的账户恢复路径未定义

- **问题**：普通用户无自助重置，只有平台级 Admin 能设置密码，但没有说明首个或最后一个平台级 Admin 无法登录时如何恢复管理能力。
- **影响**：开源部署可能因唯一管理员失去凭据而无法继续管理用户。
- **选项**：A. 提供部署侧管理员恢复命令，不属于普通用户自助流程；B. 支持多个平台 Admin 互相重置，最后一个 Admin 另走部署恢复；C. v0.1 明确不提供产品内恢复，由部署者重新初始化。
- **推荐**：B，并保留部署侧兜底恢复。
- **需要用户决定**：是。

##### RV-014 · “尽快使用最新权限范围”不可验收

- **问题**：§11、§12 多次使用“尽快”，没有明确新请求何时必须使用最新权限。
- **影响**：撤销、退出和 blocked 的生效结果无法验收。
- **选项**：A. 变更成功后的所有新请求立即使用最新权限；B. 允许明确的最大传播时间；C. 不设时限，只保证最终一致。
- **推荐**：A。符合高风险拒绝规则；性能实现不在需求文档中展开。
- **需要用户决定**：是。
- **用户决策**：A

### 2026-08-14 · 后续补充决定

- **超级管理员范围**：平台级 Admin 可以查看和管理全平台所有 Organization 及其全部资源内容。
- **组织管理员范围**：Organization owner/admin 可以查看和管理本 Organization 内全部资源，包括下级 Department、Project、个人文档、个人知识库及其中的文档。
- **知识库管理层级**：Department、Project 和个人知识库保留各自日常负责人，但 Organization owner/admin 可以管理本 Organization 内所有类型的知识库、内容和授权，不受下级负责人范围限制。
- **隔离边界**：Organization owner/admin 的超级管理权限不跨越 Organization；平台级 Admin 不受此组织范围限制。
- **个人资源含义**：个人资源默认不向其他普通成员开放，但不对 Organization owner/admin 或平台级 Admin 隐藏。
- **处理结果**：已更新当前 v0.1 的角色矩阵、知识库管理、权限查询和 Admin 任务；生命周期保持 `work`。

# 企业 RAG + Harness 用户与访问治理需求文档

**用途**：定义首版用户、组织协作与知识访问治理的产品需求，作为后续产品讨论和 Figma 原型设计输入。

**当前范围**：面向固件、上位机、半导体和制造业知识协作场景，覆盖用户身份、组织、部门、项目、KnowledgeBase、Document、授权、审批、审计与 RAG 检索权限联动。

**版本状态**：v0.1 工作稿；当前已知开放产品问题均已确认并写入，等待用户接受修改结果；尚未评审，也不是正式需求基线。

---

## 1. 产品目标与边界

平台需要为企业知识协作提供统一的用户与访问治理，使页面访问、管理操作和 RAG 查询都能基于同一套身份、组织上下文、资源关系和授权结果判断“当前用户能否对当前资源执行当前动作”。【R-0001】

本主题包含：

- 用户账户、状态与组织成员关系；
- Organization、Department 和 Project 的成员与治理关系；
- KnowledgeBase 与 Document 的所有权、共享、继承、屏蔽和撤销；
- 授权申请、审批策略、审批状态与权限生效；
- 管理后台的组织、成员、资源、授权、审批、权限查询与审计任务；
- RAG 检索前的知识访问范围收敛。【R-0001】

首版不包含完整 HR/OA、Team、通用 BPMN、管理员自定义权限 DSL，也不在本需求中确定 OpenFGA DSL、数据库表、API、服务拆分、页面布局或视觉样式。

## 2. 身份、组织与当前上下文

### 2.1 全局用户身份

User 是平台级唯一身份，不因加入不同 Organization 而复制账户。用户可以加入多个 Organization，并在各 Organization 中拥有不同的成员状态和组织角色。【R-0002】

涉及组织资源的页面、操作和 RAG 查询必须具有明确的当前 Organization。用户切换 Organization 后，系统应基于新的组织上下文重新确定可见资源和可执行操作；当前组织失效或用户已不再属于该组织时，不得继续沿用原上下文访问资源。【R-0002】【R-0017】

### 2.2 用户状态

| 状态 | 产品含义 | 用户可见结果 |
| --- | --- | --- |
| active | 正常可用 | 按当前组织和资源授权访问 |
| suspended | 暂时停用 | 拒绝业务访问，成员与授权历史保留 |
| disabled | 长期停用或离职 | 不可登录，历史审计保留 |

开源版不提供邀请或 pending 待加入流程。平台级 Admin 创建用户成功后，账户立即进入 active，无需再次启用。管理员需要能够识别用户当前状态及其访问影响；状态变更必须进入审计。【R-0003】【R-0015】【DEC-0008】

### 2.3 组织角色不等于知识权限

Organization 至少包含 owner、admin、member、guest 四类组织角色。owner/admin 负责组织治理，member 为普通成员，guest 为受限外部或临时成员。【R-0004】

组织角色与 KnowledgeBase/Document 权限分开判断。owner/admin 不因治理身份自动获得敏感知识读取权；未建立可证明的资源授权路径时，系统默认拒绝访问。【R-0004】【DEC-0001】

无权限时必须阻止操作并提供可理解的结果；具体采用隐藏、禁用或说明页，由 Figma 在不改变权限语义的前提下决定。【DEC-0006】

### 2.4 开源版账户与密码管理

开源版用户账户不通过邀请产生，只能由平台级 Admin 在后台直接创建。创建用户时由平台级 Admin 设置登录密码；创建后也只有平台级 Admin 可以为该用户设置新密码。Organization admin 不具备创建平台全局用户或修改全局用户密码的能力。【R-0018】【DEC-0007】

普通用户不能修改本人密码。登录页和个人设置不提供忘记密码、修改密码或自助重置密码入口；用户忘记密码后只能联系平台级 Admin，由平台级 Admin 设置新密码。【R-0018】

平台级 Admin 的用户创建和密码设置任务需要显示操作成功或失败结果。创建成功后账户立即进入 active，成功反馈和用户列表均应反映该状态，不提供单独的启用步骤。【R-0018】【DEC-0008】

## 3. Department 正式组织关系

Department 是 Organization 内的正式组织单元，支持多级层级。用户可同时加入任意多个 Department，不强制主部门与兼职部门模型。【R-0005】【DEC-0002】

部门管理至少需要支持：

- 浏览组织内的部门层级；
- 创建、调整和归档部门；
- 管理部门成员及多部门归属；
- 配置一个或多个部门负责人；
- 识别部门状态对成员管理和新授权的影响。【R-0005】【R-0014】

Department 负责人用于审批、治理和责任展示，不因负责人身份自动获得部门全部知识读取权。Department 存在有效授权时不得直接归档；归档任务必须先展示受影响授权，具备归档权限的管理员需要逐项迁移到其他主体、转换为其他有效授权或撤销。全部有效授权处理完成后才允许归档。【R-0005】【R-0011】【DEC-0011】

## 4. Project 跨组织协作

Project 是独立于 Department 的协作实体，归属于一个 Organization。项目至少支持 owner/manager、member、guest，并区分 internal member 与 external member。【R-0006】【DEC-0003】

项目状态至少包括 draft、active、suspended、completed、archived。不同状态需要影响成员管理、项目治理和项目来源授权的可用操作。【R-0006】

平台允许其他 Organization 的用户直接作为 external member 加入 Project。加入项目只创建项目成员关系，不自动获得项目所属 Organization 的其他资源权限。只有当 Project 被授予某个 KnowledgeBase/Document 权限时，其符合条件的成员才能通过项目路径获得相应访问。【R-0006】【R-0008】

项目可关联一个或多个 KnowledgeBase，但 KnowledgeBase 始终归 Organization 所有。项目完成或归档不转移知识资产，也不删除项目关联知识。【R-0007】【DEC-0001】

Project 进入 `completed` 后，既有项目来源授权继续有效，但不得再创建新的项目来源授权。Project 进入 `archived` 后，系统撤销项目来源授权；同一用户通过 Organization、Department、User 直授权或其他独立路径获得的权限不受影响。状态变更前需要展示新增授权限制或撤销影响。【R-0006】【R-0011】【DEC-0010】

## 5. 知识资产与授权模型

### 5.1 资源关系

- KnowledgeBase 必须归属于一个 Organization；
- KnowledgeBase 可设置负责知识治理和共享审批的负责人；
- Document 必须属于一个 KnowledgeBase，并通过该 KnowledgeBase 归属于 Organization；
- Project 可以与 KnowledgeBase 建立关联或获授权关系，但不是知识资产所有者。【R-0007】【DEC-0001】

资源详情需要区分最终所有者、负责人、关联项目和当前授权主体，避免把负责人或项目关系误认为所有权。【R-0007】

### 5.2 权限级别

| 权限      | 主要能力                             | 限制         |
| ------- | -------------------------------- | ---------- |
| viewer  | 查看 KnowledgeBase 及默认继承的 Document | 不能编辑或管理授权  |
| editor  | 查看、编辑和上传内容                       | 不能管理授权     |
| manager | 查看、编辑、共享和管理资源权限                  | 仍受审批策略约束   |
| blocked | 对指定资源显式拒绝访问                      | 用于覆盖其他允许路径 |

KnowledgeBase 可向 Organization、Department、Project 或 User 授予上述适用权限。授权任务必须指定对象类型、具体对象、权限级别和可选有效期。【R-0008】【DEC-0005】

### 5.3 多路径权限

一个用户可以同时通过 Organization、Department、Project、User 直授权和 Document 继承等路径获得权限。系统应根据全部有效路径计算最终能力，而不是只展示或保存一个“最高角色”。【R-0009】

权限查询至少应回答：

- 当前主体对目标资源拥有哪些有效能力；
- 每项能力来自直接授权、组织、部门、项目还是继承；
- 是否存在 blocked 或主体状态导致的拒绝；
- 撤销某条路径后，是否仍有其他路径维持访问。【R-0009】【R-0011】

## 6. Document 继承与例外

Document 默认继承所属 KnowledgeBase 权限，同时支持 Document 级直接授权、权限提高和 blocked。【R-0010】【DEC-0004】

最终判断遵循以下产品优先关系：

1. 用户账户或 Organization 上下文无效时，直接拒绝；
2. Document 存在适用于当前用户的 blocked 时，拒绝该 Document；
3. Document 直授权或主体集合授权可提供相应文档能力；
4. 没有文档例外时，继承 KnowledgeBase 的相应能力；
5. KnowledgeBase blocked 对继承路径生效，Document 直授权默认不能反向解除该 blocked。【R-0010】

文档权限管理需要同时呈现继承来源、文档例外、显式屏蔽和最终有效结果。更改文档授权不得改变 Document 或 KnowledgeBase 的 Organization 所有权。【R-0007】【R-0010】

## 7. 共享、撤销与到期

共享仅创建访问授权，不转移资产所有权。拥有相应共享能力的用户可以向 Organization、Department、Project 或 User 发起授权；viewer/editor 默认不能将外部共享继续转授给第三方。【R-0011】

Grant 可配置有效期。授权到期后停止提供访问，并保留历史记录。撤销 Grant 时只移除目标授权路径，不影响同一主体通过其他路径获得的权限。【R-0011】

撤销前需要让操作者核对目标资源、授权对象、权限级别、来源和影响范围。撤销后需要展示：

- 被移除的授权路径；
- 操作是否成功；
- 目标主体是否仍通过其他路径拥有权限；
- 如仍有权限，其主要来源是什么。【R-0009】【R-0011】

用户退出 Department 或 Project 后，应立即失去通过该成员关系获得的权限；用户退出 Organization 后，应失去通过该 Organization 及其 Department、Project 获得的权限。【R-0011】

## 8. 授权审批与生效

### 8.1 策略匹配

授权审批与当前权限判断是两个独立过程。系统必须提供一套始终可用的 Default Policy；管理员可按 Organization、资源类型、授权目标类型和目标权限级别配置更具体的 Approval Policy。【R-0012】

首版默认策略包括：

| 场景                                              | 默认处理                                                                    |
| ----------------------------------------------- | ----------------------------------------------------------------------- |
| 同一组织内，KnowledgeBase manager 发起 viewer/editor 分享 | 直接生效                                                                    |
| 同一组织内，普通 editor/member 发起共享                     | KnowledgeBase 负责人审批                                                     |
| 跨部门共享                                           | KnowledgeBase 负责人审批；可追加部门负责人                                            |
| 跨组织 viewer                                      | KnowledgeBase 负责人后，由源 Organization admin 审批                             |
| 跨组织 editor/manager                              | KnowledgeBase 负责人后，由源 Organization admin 审批；可要求目标 Organization admin 接受 |
| 敏感 Document 授权或解除 blocked                       | KnowledgeBase 负责人审批；可追加 Organization admin                              |

策略配置需要让管理员识别适用范围、匹配条件、审批步骤及优先顺序。发起共享后，用户应知道该请求会直接生效还是进入哪些审批步骤。【R-0012】

### 8.2 审批状态

Approval Request 至少包含以下状态：

```text
draft → pending → approved → applied
                 ├→ rejected
                 ├→ cancelled
                 └→ expired
```

`approved` 表示审批决定已经通过，`applied` 表示 Grant 与授权关系已经成功写入、权限已生效。系统不得向用户把 approved 显示为已经获得访问。【R-0013】

当审批通过但授权写入失败时，应显示独立的生效失败状态，保留申请、审批和失败信息。平台级 Admin 可对全平台失败任务执行重试、终止或转交；Organization owner/admin 可对本组织失败任务执行相同操作；申请人和审批人只能查看失败信息、处理进度与最终结果。转交目标必须是对该任务具有处理权限的角色。【R-0013】【DEC-0009】

## 9. Admin 后台任务

首版 Admin 后台需要覆盖以下任务，而不是预先锁定具体页面数量或导航结构：【R-0014】

| 任务域   | 必须支持的任务与信息                                          |
| ----- | --------------------------------------------------- |
| 组织管理  | 查看和维护组织信息、状态、owner/admin 与默认审批策略                    |
| 部门管理  | 浏览组织树，创建、调整、归档部门，维护负责人和成员；归档前查看并处理全部有效授权影响       |
| 用户管理  | 平台级 Admin 直接创建用户、设置初始密码和新密码，维护组织/部门归属，停用或恢复账户；Organization admin 不提供全局账户与密码管理操作 |
| 项目管理  | 创建项目，维护负责人和跨组织成员，变更项目状态；completed 禁止新增项目授权，archived 撤销项目来源授权 |
| 知识库管理 | 查看所有权、负责人、关联项目、状态和共享入口                              |
| 共享与授权 | 创建、查看、到期和撤销 Organization/Department/Project/User 授权 |
| 审批中心  | 待我审批、我的申请、审批历史、当前步骤和生效结果；按管理范围处理授权生效失败             |
| 策略配置  | 维护默认策略及更具体的匹配条件和审批步骤                                |
| 权限查询  | 查询主体对资源的有效能力、来源路径和拒绝原因                              |
| 审计日志  | 查询成员、组织结构、资源、授权、审批和高风险操作历史                          |

前端可根据服务端返回的 capabilities 决定入口和操作是否可用，但前端隐藏或禁用不是安全边界；服务端仍必须校验每个受保护操作。【R-0014】【R-0017】

普通用户侧不提供修改密码、忘记密码或自助重置密码入口。平台级 Admin 的用户管理入口需要能区分创建用户、设置新密码与账户状态管理，但具体页面、弹窗或抽屉形式由 Figma 决定。【R-0018】【DEC-0006】

## 10. 审计与可追溯性

以下事件至少需要进入审计：登录安全事件、Organization 成员变化、Department 成员与结构变化、Project 成员与状态变化、KnowledgeBase/Document 共享、授权变更、审批、撤销、到期、资源归档以及 blocked 变化。【R-0015】

每条审计信息至少能够识别：

- 操作者；
- 操作发生的 Organization 上下文；
- 动作；
- 目标资源类型和对象；
- 关键变更前后值或差异；
- 与请求或调用关联的标识；
- 操作时间。【R-0015】

审计查询需要帮助管理员解释“谁在何时因何操作改变了谁对什么资源的访问”，并保留被停用用户和历史资源关系的可追溯性。【R-0003】【R-0015】

## 11. RAG 查询权限联动

每次 RAG 查询必须先结合用户身份、当前 Organization 和有效授权，得到可访问的 KnowledgeBase/Document 范围，再把该范围用于检索过滤。系统不得先全库召回或让 LLM 接触未授权内容，再在输出阶段过滤。【R-0016】

KnowledgeBase 权限用于收敛知识库范围，Document 的直接授权、继承和 blocked 必须进一步作用到文档范围。权限变化后，新的检索请求应尽快使用最新范围；撤销、成员退出和 blocked 不得因缓存长期保留旧访问。【R-0010】【R-0016】【R-0017】

RAG 日志、Evaluation 数据和其他可能包含知识内容的可观测数据同样受知识访问边界约束。【R-0016】

当当前上下文没有可访问知识、目标知识已失权或授权服务不可用时，系统应拒绝检索并提供可理解的结果。授权服务不可用时不得使用缓存允许结果继续执行 RAG 查询。【R-0016】【R-0017】【DEC-0012】

## 12. 安全与一致性要求

- Organization 是默认的数据和访问隔离边界；
- 所有受保护操作由服务端基于可信身份、当前 Organization、目标资源和动作完成授权；
- 客户端不得自行声明可信的 user_id 或 organization_id；
- 未建立可证明授权路径时默认拒绝；
- 授权服务不可用时，所有受保护的写操作、只读页面、API 和 RAG 查询均拒绝；
- Grant 撤销、成员退出、用户停用和 blocked 等高风险变化应尽快影响页面、API 和 RAG 查询；
- 若缓存权限结果，必须避免撤销后继续沿用旧的允许结果。【R-0017】

授权服务不可用期间不得使用缓存允许结果降级放行。用户应看到“授权服务暂时不可用”的明确反馈以及可重试方式，不应被误导为资源不存在或本人永久失权。【R-0017】【DEC-0012】

## 13. 已确认补充决策与设计自由

### 已确认补充决策

- **DEC-0009 · 授权生效失败分级处置**：平台级 Admin 可处理全平台任务，Organization owner/admin 可处理本组织任务，申请人和审批人仅查看。
- **DEC-0010 · Project 生命周期授权结果**：completed 保留既有授权但禁止新增，archived 撤销项目来源授权。
- **DEC-0011 · Department 归档前清理授权**：存在有效授权时阻止归档，必须先迁移、转换或撤销。
- **DEC-0012 · 授权服务故障统一拒绝**：所有受保护访问均拒绝，不使用缓存允许结果降级放行。
